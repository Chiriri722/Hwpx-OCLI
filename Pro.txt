확인했습니다. **세 저장소 중 하나로 나머지를 대체하기보다는, Hwpx-OCLI의 엄격한 원본 보존·검증 구조를 중심으로 kordoc의 문서 이해·양식 편집 기능을 참고하고, hwp-mcp의 한글 프로그램 제어는 선택적인 검증 수단으로 분리하는 방향이 가장 적합합니다.**

다만 비교에 앞서 중요한 점이 있습니다. **조회된 Hwpx-OCLI의 `main`과 실제 한컴 기능을 개발하는 `feat/hwpx-plugin` 브랜치가 다릅니다.** 아래에서는 HWPX 기능이 들어 있는 `feat/hwpx-plugin`의 실제 구현을 중심으로 비교했습니다. 기본 브랜치만 보면 사용자님의 한컴 문서 처리 기능을 상당 부분 놓치게 됩니다. 

이번 검토는 저장소의 핵심 코드·기능 선언·검증 문서를 대조한 **정적 분석**입니다. 한글 프로그램을 설치해 실행하거나, 세 도구로 같은 문서를 처리해 실제 화면·출력물을 비교하는 실험까지 수행한 것은 아닙니다. 따라서 코드에서 확인되는 지원 범위와 실제 문서 호환성을 구분해 설명하겠습니다.

이 표는 각 저장소의 실제 매니페스트, 읽기·쓰기 분기, 공개 API를 기준으로 정리했습니다. 특히 kordoc은 이번에 조회한 `package.json` 기준 **4.16.0, Node.js 20 이상을 요구하는 TypeScript 프로젝트**입니다.      

**여기서 가장 조심해야 하는 것은 “파일을 읽을 수 있다”, “변환 결과에 표를 보존한다”, “원본 표를 편집할 수 있다”를 같은 기능으로 취급하지 않는 것입니다.** 사용자님의 저장소도 바로 이 구분에 따라 평가해야 합니다.

# 2. Hwpx-OCLI: 이미 강한 부분과 실제로 부족한 부분

## 2-1. 현재 구조는 ‘HWPX 기능을 조금 추가한 CLI’보다 훨씬 넓습니다

실제 작업 브랜치의 `plugins/hancom`은 역할이 다른 네 바이너리로 분리되어 있습니다.

| 바이너리 | 담당 기능 |
|---|---|
| `officecli-hancom-hwpx` | HWPX·OWPML을 직접 열고 조회·제한적 텍스트 수정 |
| `officecli-hancom-hwp` | HWP·HML을 OfficeCLI의 DOCX 생성 명령으로 변환 |
| `officecli-hancom-cell` | 검증된 Cell OOXML 파일을 XLSX 형제 파일로 복사 |
| `officecli-hancom-show` | 검증된 Show OOXML 파일을 PPTX 형제 파일로 복사 |

HWPX는 원본 패키지를 직접 다루지만, HWP와 HML은 DOCX 쪽으로 옮기는 경로입니다. 바이너리 HWP는 선택적인 RHWP를 이용해 임시 HWPX로 바꾼 뒤 처리합니다. **따라서 HWP를 읽고 나온 DOCX를 수정하더라도, 그 수정이 원본 HWP로 되돌아가는 구조는 아닙니다.** 

이 분리는 유지하는 편이 좋습니다. 읽기·변환·원본 수정의 책임이 분명하기 때문에, 나중에 기능을 확장하더라도 잘못된 쓰기가 다른 형식으로 번지는 것을 막기 쉽습니다.

## 2-2. 가장 큰 장점은 ‘원본 보존을 검증하는 저장 구조’입니다

`owpml/editor.rs`는 단순히 ZIP을 열고 XML을 수정한 뒤 다시 압축하는 수준이 아닙니다.

원본 ZIP 엔트리별로 압축 해제된 내용의 해시, 압축된 데이터의 해시, CRC, 크기, 압축 방식, 시간·권한·주석·추가 데이터 등을 기록하고, **변경 계획에 포함된 부분만 바뀌었는지** 검사합니다. 엔트리의 이름과 순서도 검증 대상입니다. 

실제 저장 경로에서도 같은 디렉터리에 임시 파일을 만들고, 수정본을 재검증하고, 디스크에 기록한 다음 원본을 교체하도록 구성되어 있습니다. 편집 대상은 기존 텍스트와 연결되며, 외부에서 원본이 바뀌었는지도 확인합니다. 

**이 부분은 다른 저장소의 기능을 가져오면서 약화시키면 안 됩니다.**

예를 들어 kordoc의 편집 범위가 더 넓다고 해서 그 출력 파일을 곧바로 원본에 덮어쓰는 식으로 연결하면, 사용자님이 이미 구축한 “허용한 변경만 반영한다”는 보장이 사라질 수 있습니다.

다만 현재 검증기의 설명에도 명시되어 있듯이, 이 검사는 **구조·보안·재열기 가능성에 관한 검증이지, KS X 6101 전체나 모든 XSD에 대한 완전한 적합성 인증은 아닙니다.** 한글에서의 시각적 동일성까지 자동으로 보장하는 것도 아닙니다. 

## 2-3. 현재 HWPX 직접 편집 범위는 의도적으로 좁습니다

`format_handler.rs`의 기능 선언을 보면 매우 명확합니다.

```text
추가 가능한 객체 종류: 없음
설정 가능한 속성: text
노드 종류: document / section / paragraph / text
```

읽기 전용 세션은 `view`, `get`, `query`, `validate`, `raw`를 제공하고, 편집 가능한 세션에서만 `set`, `save`가 추가됩니다. `add`, `remove`, `move`, `copy`, `raw_set`, `add_part`, `extract_binary` 등은 현재 직접 HWPX 경로에서 명시적으로 거부합니다.  

그러므로 현 상태를 다음처럼 구분해야 합니다.

> **HWPX의 표·그림·각주·스타일을 읽어 DOCX로 옮기는 기능은 넓지만, HWPX 원본의 표·그림·각주·스타일을 자유롭게 편집하는 기능은 아직 아닙니다.**

변환 쪽에는 병합표, 중첩표, 이미지, 각주·미주, 머리말·꼬리말, 동적 페이지 번호, 목록 번호, 이름 스타일, 수식, 제한된 도형과 차트의 매핑이 문서화되어 있습니다. 하지만 그것은 DOCX 투영 경로의 지원 범위입니다. 

이 점은 README·도구 설명에서도 더 전면에 표시하는 것이 좋습니다. AI가 “표를 읽을 수 있으니 표 행도 추가할 수 있겠지”라고 잘못 추론하기 쉬운 지점이기 때문입니다.

## 2-4. 당장 보완할 부분은 편집보다 ‘읽기 결과의 구조와 진단’입니다

코드에서 확인한 가장 분명한 보완점은 `view` 구현입니다.

현재 직접 HWPX 경로에서 `outline`은 빈 문자열 또는 빈 `items`를, `issues`는 빈 배열을 반환합니다. `query`도 문서·구역·문단·텍스트 또는 정확한 경로만 대상으로 하며, 표나 셀을 의미 단위로 질의하는 인터페이스는 없습니다. 

이것은 단순한 편의성 문제를 넘어 결과 해석에 영향을 줍니다.

- 빈 목차는 “제목이 없는 문서”처럼 보일 수 있습니다.
- 빈 문제 목록은 “검사했는데 문제가 없다”처럼 보일 수 있습니다.
- 표 안의 텍스트가 읽혀도 “어느 행·열·병합 셀에 속하는가”가 별도 객체로 드러나지 않으면, AI가 숫자와 항목의 관계를 잘못 이해하기 쉽습니다.

따라서 우선 **미구현 상태와 실제 빈 결과를 구분**해야 합니다. 구현 전이라면 `unsupported_feature`나 명시적인 상태를 반환하고, 구현 후에는 분석 범위를 함께 표시하는 방식이 적절합니다.

반대로, 저장소의 9월 8일 검토 기록에서 지적했던 혼합 텍스트·CDATA 읽기 누락과 `//text` 선택자 문제는 **후속 수정 완료로 기록되어 있으며, 이번에 읽은 코드에도 관련 수정이 반영되어 있습니다.** 이를 아직 남은 결함처럼 다시 제안하지는 않겠습니다.  

## 2-5. Cell·Show 지원은 차별점이지만, 범위를 넓게 광고하면 안 됩니다

현재 지원은 일반적인 한셀·한쇼 파일 변환기가 아닙니다. **Cell 12.0300, Show 12.0000의 관측된 OOXML 기반 형식**을 검증하고, 바이트가 같은 XLSX·PPTX 형제 파일을 만드는 경로입니다.

문서에는 지원 근거가 Cell 공개 표본 한 개와 Show 공개 표본 세 개라고 명시되어 있고, `.nxl`, CFB 기반 구형 Cell·Show 및 다른 생산자 빌드는 지원 범위 밖입니다. 또한 그 형식을 나타내는 표식은 생산자를 인증하는 수단이 아니라고 분명히 구분합니다.  

**이렇게 지원 범위를 좁고 정확하게 표현하는 태도는 유지할 가치가 있습니다.** kordoc의 XLSX 읽기 기능을 붙이는 것과, 모든 `.cell` 세대를 지원하는 것은 전혀 다른 작업입니다.

# 3. hwp-mcp: ‘문서 파서’보다 ‘실제 한글을 조작하는 도구’로 참고해야 합니다

## 3-1. Windows COM 경로와 독립 읽기 경로를 분리해서 봐야 합니다

hwp-mcp에는 두 가지 성격의 기능이 공존합니다.

주요 편집 기능은 `HWPFrame.HwpObject`에 연결해 한글 프로그램의 `HAction`과 파라미터 집합을 호출합니다. 기존 실행 인스턴스에 연결을 시도하고, 실패하면 `Dispatch`로 연결합니다. 문서 생성·열기·저장·텍스트 삽입·표 작업 같은 작업은 이 경로입니다. 

반면 `src/tools/hwp_reader.py`는 한글 프로그램 없이 HWP 5.x의 OLE 스트림을 직접 읽고, 압축을 해제하고, 레코드 트리를 구성해 텍스트와 표를 추출합니다. 이 부분은 Windows 이외의 환경에서도 사용할 수 있습니다. 

즉, 다음 두 설명은 모두 부정확합니다.

> “hwp-mcp는 Windows에서만 돌아간다.”

> “hwp-mcp는 한글 없이 모든 기능을 사용할 수 있다.”

정확하게는 **독립 HWP 읽기는 여러 운영체제에서 가능하고, 주요 편집 기능은 Windows와 설치된 한글 프로그램에 의존합니다.** 

## 3-2. 특히 주의할 점: 현재 저장 코드가 HWP로 고정되어 있습니다

`HwpController`의 실제 코드를 보면 다음과 같습니다.

```python
# 열기
pset.Format = "HWP"

# 다른 이름으로 저장
self.hwp.SaveAs(abs_path, "HWP", "")
```

따라서 **파일명만 `결과.hwpx`로 지정한다고 HWPX로 저장되는 코드가 아닙니다.** 한글 프로그램 자체의 지원 포맷과, 이 MCP 래퍼가 실제로 노출한 포맷 지원을 구분해야 합니다. 

또한 이 저장 함수는 `SaveAs` 호출 후 반환값을 별도로 검사하지 않고 `True`를 반환하는 경로가 있습니다. 코드상으로는 “예외가 발생하지 않았다”와 “원하는 형식의 파일이 올바르게 만들어졌다”가 충분히 구분되지 않습니다. 사용자님의 도구에 이 방식을 반영한다면, 호출 결과뿐 아니라 **산출물 존재 여부·실제 형식·재열기 결과까지 검증**하도록 강화해야 합니다. 

## 3-3. 독립 읽기 모듈은 간단하지만, 사용자님의 파서를 대체할 정도는 아닙니다

직접 읽기 모듈은 HWP 5.x만 대상으로 하며 HWPX와 HWP 3.x는 명시적으로 거부합니다. 암호가 설정된 문서와 배포용 문서도 본문 읽기 경로에서 거부합니다. 

표 처리도 범위를 잘 봐야 합니다. 코드에서 `rowspan`, `colspan`은 읽지만, 최종 출력 격자에서는 셀의 시작 위치에만 텍스트를 넣습니다. Markdown 출력에서는 첫 행을 헤더 형태로 내보냅니다.

따라서 얻는 것은 다음에 가깝습니다.

> **표 안의 내용을 순서대로 읽을 수 있는 텍스트 표현**

다음과 같지는 않습니다.

> **병합 관계·다단 헤더 의미·서식까지 보존한 원본 표 모델**

이 차이는 공문서의 결재란, 신청서, 다단 병합표에서 중요합니다. 

본문 파싱에 실패했을 때 `PrvText` 미리보기 텍스트를 반환하는 경로도 있습니다. 다행히 현재 서버는 이를 숨기지 않고 “본문을 읽을 수 없어 미리보기 텍스트를 반환한다”는 설명을 붙입니다. 다만 사용자님의 도구에 가져온다면 설명 문자열에만 의존하지 말고, `source=preview`, `completeness=partial` 같은 구조화된 상태로 구분하는 편이 더 안전합니다. 

추가로, 해당 간단 파서를 그대로 가져오려면 레코드 길이 경계, 압축 해제량, 표 행·열 수에 대한 자원 제한을 보강해야 합니다. 이는 코드에서 확인되는 방어 수준에 대한 지적이며, 실제 공격 파일로 장애를 재현했다는 뜻은 아닙니다. 사용자님의 기존 Rust 패키지 검증 구조를 이 모듈로 교체할 이유는 약합니다. 

## 3-4. 가장 가치 있는 활용은 ‘실제 한글을 이용한 확인 장치’입니다

hwp-mcp에서 가져올 만한 핵심은 **한글 프로그램을 통해 결과를 확인하는 방법**입니다.

사용자님의 파서가 만든 파일을 한글로 열고, 저장 또는 변환한 결과를 다시 분석하면 “XML이 유효하다”를 넘어 “한글이 이 문서를 어떻게 해석했는가”를 확인할 수 있습니다. 이는 현재의 구조 검증을 보완하는 방법으로 적합합니다.

하지만 hwp-mcp의 연결 방식은 기존 활성 한글 인스턴스에 연결할 수 있고, 문서 닫기·전체 닫기와 대화상자 억제 기능도 있습니다. 보안 모듈 등록도 연결 함수에서 기본적으로 활성화되어 있습니다. 

따라서 그대로 기본 기능으로 넣기보다는, **테스트용 복사본과 분리된 한글 인스턴스만 사용하는 선택적 검증 프로그램**으로 만드는 편을 권합니다. 사용자가 작업 중인 문서에 연결하거나, 저장 확인을 조용히 생략하는 동작을 기본값으로 삼아서는 안 됩니다.

# 4. kordoc: 가장 많이 참고할 수 있지만, 그대로 붙이면 정책 충돌이 생깁니다

## 4-1. 가장 큰 차이는 ‘AI가 이해할 수 있는 문서 모델’입니다

kordoc의 파싱 결과는 단순 문자열만이 아닙니다. 포맷에 따라 Markdown, 블록 구조, 메타데이터, 목차, 경고, 이미지, 페이지 정보를 반환합니다. HWPX·HWP 5.x·HWP 3.x·HWPML을 별도 파서로 다루며, ZIP·OLE 내부 형식도 구분합니다.  

이것이 현재 Hwpx-OCLI 직접 HWPX 읽기 경로와 가장 크게 차이 나는 부분입니다.

예를 들어 사용자가 다음처럼 요청할 때 차이가 납니다.

> “신청서에서 성명과 주소 입력란을 찾아 채워 줘.”

텍스트만 나열하면 “성명”이라는 문자열을 찾는 것까지는 쉽지만, 그 오른쪽 셀이 입력란인지, 다른 표에도 같은 항목이 있는지, 병합된 칸인지 판단하기 어렵습니다. 반면 문서 블록·표·셀·원본 위치가 연결되어 있으면 그 판단과 검증을 구조적으로 수행할 수 있습니다.

**사용자님의 저장소에서 가장 먼저 참고할 대상은 새로운 HWP 파서보다 이 상위 문서 모델입니다.**

## 4-2. 편집 전에 가능 여부를 알려주는 설계가 좋습니다

`src/roundtrip/session.ts`는 블록별로 다음과 같은 편집 가능 상태를 제공합니다.

```text
text       : 문단 텍스트 편집 가능
cell-text  : 표 셀 텍스트 편집 가능
locked     : 편집 불가, 이유 제공
```

표는 셀마다 편집 가능 여부를 반환하고, 원본 위치를 가리키는 `sourceRef`도 제공합니다. 매핑이 실패하거나, 문단이 여러 조각으로 분리되거나, 강제 줄바꿈 때문에 안전한 수정이 어려운 경우에는 잠금 사유를 반환합니다. 

사용자님의 현재 구현도 쓰기 가능 범위를 엄격히 제한하고 있으므로, 이 설계와 잘 맞습니다. 다만 개선 방향은 단순히 잠금 여부 하나를 추가하는 것이 아니라 다음을 함께 보여주는 것입니다.

```text
이 텍스트는 읽을 수 있는가?
어떤 원본 위치에서 읽었는가?
현재 수정할 수 있는가?
수정할 수 없다면 무엇 때문에 막혔는가?
어떤 다른 작업은 가능한가?
```

이렇게 하면 AI가 실패할 작업을 반복하지 않고, 사용자에게 “이 칸은 읽을 수 있지만 현재는 원본 보존 편집 범위 밖”이라고 설명할 수 있습니다.

한 가지 주의할 점은 kordoc의 세션 블록 인덱스가 영구 식별자는 아니라는 것입니다. 코드는 패치 후 전체 상태를 재구축하며 이전 블록 인덱스가 무효화된다고 명시합니다. 이를 참고하되 사용자님의 인터페이스에는 문서 revision이나 원본 해시를 함께 연결하는 것이 좋습니다. 

## 4-3. 원본 패치는 사용자님보다 넓지만, ‘부분 성공’ 정책입니다

kordoc의 HWPX 패치는 문단·셀 텍스트뿐 아니라 제한적인 문단→표 변환과 표 행 추가·삭제도 다룹니다. 반면 블록 추가·삭제·순서 변경, 표 열·병합 변경, 주석·머리말·이미지 변경 등은 지원 범위 밖이거나 건너뛰는 대상으로 구분합니다. 

바이너리 HWP 5.x도 `PARA_TEXT`만 바꾸고 끝내지 않습니다. 문단 문자 수, 글자 모양 위치, 줄 레코드, 레코드 길이, 압축 스트림과 CFB 구조를 함께 갱신하며, 원본 레코드를 동일하게 재직렬화할 수 있는지 등의 조건을 검사합니다. 따라서 이는 **제한적인 HWP 원본 패처이지, 모든 HWP를 자유롭게 생성·편집하는 엔진은 아닙니다.** 

여기서 특히 중요한 차이가 있습니다.

**kordoc의 `patchHwpx()`는 `success: true`와 `skipped`를 동시에 반환할 수 있습니다.** 자동 검증도 재파싱 후 편집 Markdown과의 차이를 반환하지만, 모든 요청이 완벽히 일치해야만 `success`가 되는 구조는 아닙니다. 

사용자님의 엄격한 저장 방식과 결합할 때는 다음처럼 해석해야 합니다.

> `success`는 “패치 처리가 성립했다”는 의미로 보고,  
> **“사용자가 요청한 변경이 모두 반영되었다”는 판정은 별도로 수행한다.**

`skipped`, 실제 적용 수, 검증 결과를 확인하지 않고 성공만 보고 저장 완료로 표시하는 연결은 피해야 합니다.

## 4-4. ‘kordoc은 손실 변환, Hwpx-OCLI는 무손실’이라는 단순 구분도 틀립니다

kordoc 역시 원본 보존을 위한 전용 ZIP 패치 코드를 갖고 있습니다.

`zip-patch.ts`는 JSZip으로 전체 파일을 다시 직렬화하면 바이트 보존이 깨진다는 점을 명시하고, 변경되지 않은 로컬 레코드를 그대로 복사하며 필요한 오프셋 등을 갱신하는 방식으로 구현되어 있습니다. 

따라서 차이는 다음에 있습니다.

- 사용자님의 구현은 변경 허용 범위와 저장 검증을 좁고 엄격하게 설정합니다.
- kordoc은 더 넓은 편집 작업을 제공하면서, 불가능한 변경을 건너뛰고 결과를 보고하는 방식을 사용합니다.

또한 kordoc은 **원본 패치와 새 문서 생성을 별도 기능으로 구분**합니다. `hwpx-preserve`는 원본 ZIP을 수정하는 경로이고, 일반 `hwpx` 생성은 중간 문서 표현과 Markdown을 거쳐 새 파일을 만드는 경로라 스타일이 초기화될 수 있다고 명시합니다. 

사용자님의 CLI에서도 “원본 수정”, “다른 형식으로 변환”, “내용을 바탕으로 새 문서 생성”을 명령과 결과에서 명확하게 나누는 것이 좋습니다.

## 4-5. 표 처리에서 배울 점과 그대로 가져오면 안 되는 점

kordoc은 `rowSpan`, `colSpan`, 셀 주소를 활용하는 표 모델을 갖고 있으며, 실제 셀 주소에 따라 격자를 구성합니다. 이는 hwp-mcp의 간단한 Markdown 표 출력보다 풍부한 구조입니다. 

하지만 읽기 편의를 위한 복구 정책도 들어 있습니다. 예를 들어 해당 표 빌더는 충돌하는 셀의 텍스트를 이어 붙이거나, 범위를 벗어난 병합을 잘라내거나, 옵션에 따라 빈 후행 열을 제거합니다. 빈 입력란을 유지하기 위한 `keepAnchoredEmptyCols` 옵션도 별도로 존재합니다. 

이것은 “최대한 내용을 읽어 주는 도구”에서는 유용하지만, 원본 구조를 엄격하게 보존하려는 도구에서는 정책을 분리해야 합니다.

제안하는 구분은 다음과 같습니다.

| 모드 | 권장 정책 |
|---|---|
| 정확한 구조 읽기 | 원본 셀 주소·빈 칸·병합 정보를 그대로 표현하고, 이상 구조는 진단 |
| 복구 읽기 | 읽을 수 있는 내용을 최대한 반환하되 복구한 위치와 규칙을 표시 |
| 원본 편집 | 복구로 추정한 구조를 근거로 원본을 수정하지 않음 |

**특히 신청서의 빈 칸은 “내용이 없으니 제거해도 되는 부분”이 아니라 편집 대상 자체입니다.** 표 처리 기능을 가져온다면 이 차이를 먼저 반영해야 합니다.

## 4-6. 미리보기와 조판 캐시 처리는 별도로 참고할 가치가 있습니다

kordoc의 렌더링 코드는 HWPX에 저장된 줄·셀·개체 위치를 이용한 SVG 재현과, 캐시가 없는 경우를 위한 선택적 reflow 경로를 제공합니다. 렌더 결과에는 경고와 객체 영역 정보도 포함됩니다. 다만 이것을 한글의 모든 조판을 동일하게 재현하는 엔진으로 간주해서는 안 됩니다. 

더 중요한 부분은 패치 후의 캐시 처리입니다. `patcher.ts`는 텍스트가 바뀐 구역의 `linesegarray`를 제거해 기존 줄 배치 캐시와 새 텍스트가 어긋나지 않게 합니다. 

사용자님의 도구에서도 **텍스트 치환 후의 조판 캐시와 미리보기 일관성은 별도 검증 항목으로 올릴 필요가 있습니다.** 다만 kordoc의 캐시 삭제 방식을 그대로 복사하기보다는, 어떤 파생 데이터를 바꾸거나 무효화할 수 있는지 변경 계획에 명시해야 기존 원본 보존 정책과 충돌하지 않습니다.

# 5. Hwpx-OCLI에 반영할 구체적인 개선안

## 5-1. 최우선: 배포 브랜치·호스트·기능 선언을 일치시키기

현재는 작업 브랜치에 기능이 있고 기본 브랜치의 호스트 구현은 다릅니다. 실제 `main`의 팩토리 코드에는 format-handler 연결이 아직 구현되지 않았다는 분기가 있는 반면, 작업 브랜치에는 별도 세션 구현과 수정 기록이 있습니다. 또한 플러그인 README는 필요한 lifecycle 계약이 없는 이전 호스트 릴리스를 지원하지 않는다고 명시합니다.   

따라서 기능 추가보다 먼저 다음 상태를 사용자가 확인할 수 있어야 합니다.

```text
현재 실행 중인 OfficeCLI 버전
현재 선택된 한컴 플러그인 경로·버전
입력 파일의 실제 형식
선택된 처리 경로
읽기 가능 범위
쓰기 가능 범위
호스트와 플러그인의 호환 여부
```

새로운 `doctor` 또는 기능 진단 출력을 제안합니다. 단순히 실행 파일이 발견되었다는 것만 확인하지 말고, 실제 open·capability 응답까지 검사하는 방식이 적절합니다.

## 5-2. 첫 번째 기능 확장: 기존 문서 모델을 읽기 인터페이스까지 연결하기

새 파서를 추가하기 전에 사용자님의 기존 `hancom-core/model.rs`와 OWPML 파서를 활용하는 편이 좋습니다. 현재도 파서와 DOCX 출력기는 공통 문서 모델을 사이에 두고 분리되어 있습니다. 

추천 구조는 다음과 같습니다.

```text
HWPX 패키지
   │
   ├─ 의미 구조
   │    문단 / 제목 / 표 / 셀 / 주석 / 이미지 / 필드
   │          ↓
   │    읽기 · 목차 · 검색 · 비교 · 요약용 분할
   │
   └─ 원본 위치와 편집 가능 범위
        XML 파트 / 노드 위치 / 기존 텍스트 / 문서 revision
                   ↓
          제한된 변경 계획
                   ↓
          기존 COW + G0~G3 검증
```

핵심은 **읽기 모델을 풍부하게 만들되, 그것을 그대로 쓰기 권한으로 연결하지 않는 것**입니다.

표를 읽기 모델에 노출했다고 해서 표 행 추가를 즉시 허용할 필요는 없습니다. 대신 “표 구조는 읽을 수 있고, 이 셀의 특정 텍스트만 현재 수정할 수 있다”는 식으로 제공하면 됩니다.

이 방식이 kordoc의 장점을 반영하면서 기존 안전성을 가장 덜 흔드는 개선입니다.

## 5-3. 다음 편집 기능은 ‘임의 구조 편집’보다 ‘양식의 지정된 칸 채우기’

일반적인 `add/remove`를 먼저 넓히기보다, 공문서에서 자주 쓰는 다음 유형부터 제한적으로 지원하는 편을 권합니다.

> 지정된 누름틀, 명확한 표 셀, 미리 정의된 텍스트 자리표시자에 값을 넣는다.

kordoc에는 누름틀 추출, 양식 필드 인식, 원본 HWPX 양식 채우기, 블록·셀 편집 가능성 판단을 위한 API가 있습니다. 이 기능들의 인터페이스를 참고할 수 있습니다.  

다만 구현 시에는 다음 문제를 명시적으로 처리해야 합니다.

| 상황 | 필요한 정책 |
|---|---|
| 같은 “성명” 항목이 여러 곳에 존재 | 첫 번째 항목을 임의 선택하지 말고 원본 위치로 구분 |
| 자리표시자가 여러 글자 런에 나뉨 | 단순 문자열 치환 금지, 런·서식 경계를 인식 |
| 빈 `hp:t`가 존재 | 빈 텍스트 채우기 지원 범위 정의 |
| 텍스트 노드 자체가 없음 | 기존 텍스트 치환과 구조 추가를 구분 |
| 이미지·필드·제어문자가 섞인 셀 | 읽기 가능 여부와 편집 가능 여부를 별도 판정 |
| 요청 일부만 반영 가능 | 부분 적용 목록을 먼저 제시하고, 전체 성공으로 표시하지 않음 |

이 순서가 사용자에게 실질적인 가치를 주면서도 검증 범위를 관리하기 쉽습니다.

## 5-4. 문서 비교는 Markdown 비교와 원본 구조 비교를 분리하기

kordoc의 `compare`, `diffBlocks`, `blocksToChunks` 같은 기능은 문서를 읽고 분석하는 상위 기능의 참고 대상으로 적합합니다. 

다만 사용자님의 비교 기능은 두 종류로 나누는 것이 좋습니다.

**내용 비교**는 문장·숫자·셀 값이 어떻게 달라졌는지를 보여줍니다. **구조 비교**는 표 병합, 빈 입력란, 주석, 필드, 이미지 참조, 스타일 연결 등이 어떻게 달라졌는지를 보여줍니다.

예를 들어 셀 병합이 바뀌었는데 텍스트는 같을 수 있습니다. Markdown만 비교하면 동일해 보이지만, 신청서나 집계표에서는 의미가 달라질 수 있습니다. 따라서 변경 보고에는 원본 위치를 함께 남기는 편이 좋습니다.

## 5-5. 한글 프로그램 제어는 선택적 검증 경로로 분리하기

hwp-mcp를 참고해 별도 검증 도구를 만든다면 다음 역할에 한정하는 것이 적절합니다.

```text
테스트용 문서 복사본
   → 분리된 한글 인스턴스에서 열기
   → 경고·실패 여부 확인
   → 지정 형식으로 출력
   → 텍스트·표 구조·페이지 결과 재검사
```

이때 기존 활성 문서 연결, 무조건적인 보안 모듈 등록, 대화상자 일괄 억제는 기본 동작에서 제외하는 편이 좋습니다. 현재 hwp-mcp가 제공하는 편의 기능과 사용자님의 안전한 문서 처리 정책을 그대로 동일시할 필요는 없습니다. 

특히 텍스트가 길어졌을 때 줄바꿈, 좁은 표 셀의 넘침, 페이지 이동, 각주 위치가 어떻게 바뀌는지를 확인하는 데 이 경로를 활용할 수 있습니다. 구조 검사와 시각 검사는 서로 대체 관계가 아니라 보완 관계입니다.

## 5-6. 바이너리 HWP 직접 편집은 후순위로 두는 편이 좋습니다

kordoc의 HWP 5.x 패치는 참고 가치가 있지만, 사용자님의 현 구조에는 새로운 책임이 크게 추가됩니다. 텍스트를 바꾸는 것뿐 아니라 문자 수·서식 위치·줄 레코드·압축·CFB 스트림을 함께 맞춰야 하기 때문입니다. 

따라서 저는 다음 순서를 권합니다.

> **HWPX 읽기 구조 고도화 → 안전한 양식 채우기 → 편집 후 렌더 검증 → 필요성이 확인된 경우 HWP 5.x 직접 패치**

현재 RHWP를 이용한 HWP 읽기·변환 경로가 이미 있으므로, 단순히 “외부 프로젝트에도 HWP 파서가 있다”는 이유만으로 또 하나의 파서를 핵심 경로에 추가할 필요는 없습니다.

# 6. 실제 적용 우선순위

| 우선순위 | 작업 | 완료 여부를 판단할 기준 |
|---|---|---|
| **P0** | 작업 브랜치·호스트·플러그인 호환성 정리 | 설치된 조합이 실제 HWPX open·read·set·save 계약을 통과 |
| **P0** | 빈 `outline`·`issues`의 의미 정리 | 미구현·검사 안 함·실제 빈 결과가 서로 구분됨 |
| **P1** | 표·셀·주석·필드가 포함된 읽기 모델 | 텍스트뿐 아니라 소속 구조와 원본 위치를 조회 가능 |
| **P1** | 블록·셀별 편집 가능성 공개 | 실행 전에 가능한 작업과 거부 이유를 확인 가능 |
| **P1** | 제한된 양식 채우기 | 중복 항목·빈 칸·분할 런·혼합 셀에서 오입력 없이 검증 |
| **P1** | 텍스트 변경 후 캐시·렌더 검증 | 긴 텍스트·표 넘침·페이지 이동 사례를 실제 한글 결과와 대조 |
| **P2** | 내용·구조 비교와 문서 분할 읽기 | 변경 위치·생략 범위·원문 연결을 유지한 결과 제공 |
| **후순위** | HWP 바이너리 직접 패치·광범위한 구조 편집 | 실제 수요와 별도 회귀 자료를 확보한 뒤 지원 범위를 확장 |

코드를 가져오는 경우에는 라이선스도 저장소 전체 이름만 보고 판단하지 않는 것이 좋습니다. 현재 한컴 플러그인 README는 MIT를, kordoc의 `package.json`도 MIT를 명시합니다. hwp-mcp 역시 README에서 MIT를 선언하지만, 이번에 조회한 루트 목록에는 그 README가 가리키는 `LICENSE` 파일이 보이지 않았으므로 재사용 전에 실제 배포 고지를 확인하는 편이 안전합니다.

# 최종 판단

**Hwpx-OCLI는 저장·보존·검증의 기반이 약한 프로젝트가 아닙니다. 오히려 허용되지 않은 변경을 막고, 원본 패키지를 보존하며, 지원하지 않는 구조를 함부로 추측하지 않는 쪽에 상당한 설계가 들어가 있습니다.** 현재 더 크게 개선할 부분은 그 기반 위에서 **AI가 문서의 구조와 편집 가능 범위를 충분히 이해하도록 만드는 인터페이스**입니다.   

따라서 **kordoc에서는 구조화된 읽기·원본 위치 연결·편집 가능성 판정·양식 채우기·비교를**, **hwp-mcp에서는 실제 한글을 통한 확인 방법을** 참고하는 조합을 권합니다.

가장 먼저 진행할 한 가지를 고르면 **“HWPX 직접 읽기 경로에 표·셀·주석·필드와 원본 위치를 노출하되, 기존의 제한적 쓰기 정책은 유지하는 작업”**입니다. 이 작업이 갖춰지면 양식 채우기와 문서 비교를 같은 기반 위에 올릴 수 있고, 기능을 늘리면서도 지금의 원본 보존 설계를 유지할 수 있습니다.
